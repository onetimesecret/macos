Issue #198 (ADR-0033) gave `PageModel` one `owner` and guarded the presentation fields (2026-09-18, branch feature/198-presentation-ownership).

- A claim names its surface and is declined for a window that does not own. A release (`retireEditor`, `withdrawPasteboardOffer`, the roll geometry reset) is guarded by identity, never by ownership. **Why:** SwiftUI dismantles the old mount after the owner has moved, so an ownership guard on a release would trap in every hand off.
- `BackdropModel` settles the owner before it publishes a stance, and keeps `panelRaised` as the committed posture. **Why:** `@Published` fires on willSet and the window controller orders windows inside that turn, so key delegates of both windows come back in while `stance` still names the posture being left. `owner` is `@Published` too, so never add a subscriber that acts on `$owner` synchronously. `PrimaryEditorWindowController` hops a turn for that reason.
- A declined write is an `assertionFailure` in debug, and the user's dev build is debug. **How to apply:** every new writer asks `model.owner == surface` first, and tests watch a refusal through `Seams.declinedPresentationWrite`. `BackdropModelTests.ephemeralPages` fails the test on any refusal.
- A page's storage carries a layout manager exactly while an editor is mounted on it. A transfer and both dismantles take the editor off through `Coordinator.leavePage`, and the shed in `makeInkTextView` is only the backstop for SwiftUI building a replacement before it dismantles. **Why:** the storage owns whatever is attached to it, so a dismantled editor left on went on laying out a background page whenever the next mount was over a different page. **How to apply:** any new teardown path calls `leavePage`, and a mount that outlives a hand off is put back by the next owned pass (`updatePage`, the roll's ordinary pass), so never assume `currentSheet` is non nil on a standing mount.
- Mount sites ask `model.owner == coordinator.surface` quietly and get an empty scroller or an unclaimed roll. `makeInkTextView` (now optional) and `moveEditor` are the loud backstops through `admits`. `EditorOwnershipSequenceTests` walks both windows through seeded event sequences with SwiftUI's pass played in both orders and sometimes skipped. It found the dismantle leak above, so extend its `Event` enum when a new route moves ownership.
- A hand off owes the incoming editor the keyboard, and the debt is settled in `PageModel.reportKeys` when the owner's window first reports the keys, never by a controller. **Why:** the receiving window is often key before SwiftUI builds its editor (a summon keys the panel inside the raise, a click keys the editor window before the page moves), and a focus call tied to a reorder is skipped exactly when the window is key already. **How to apply:** a new route that moves ownership needs no focus call of its own, and a key gain with no transfer before it must keep taking nothing.
- `PageModel.holdsKeys` is the owner's key fact, not a window's. The focus rules may read it bare, since the editor they focus is the owner's. Anything a surface draws from the keyboard reads `holdsKeys(on:)`. **Why:** the card's ember border read it bare and stayed lit on a resting card for as long as the person typed in a keyed editor window. **How to apply:** B3's glance (issue 199) and any editor window chrome ask with their own surface.
- The roll's offset is carried only by a transfer, as `PageViewStates.rollPlace` (page plus `ScrollAnchor`), read through the roll geometry claim before `leavePage` empties a row, taken once by `updateRoll`, dropped by `anchorOnToday`. A roll rebuilt in its own window still opens at Day 0 (issue #79).
- `PresentationOwner.resolve` reads `panelMayOwn` first: under the never grant policy the editor window owns in all four rows, so with it shut the page is mounted nowhere. `BackdropModel.init` settles the owner for that reason. Under the policy the summon toggle never reads a raised card as keyed and the editor window taking keys does not rest the panel, both unaddressed because the policy does not ship. A third debt: Esc never reaches a panel that does not own, since the editor, the empty state catcher and the keymap are all mounted by the owner only and OnetimePad handles no key itself. **How to apply:** anything that makes a window a non owner while it is key needs its own Esc route; do not assume Esc works because `escape()` exists.
- `windowWillClose` tells the model before it drops the content view, so the transfer reads the place from an editor still in a sized scroller. When `NSHostingView` dismantles is unverified, and the sequence harness leaves a closed window's mount for the next pass on purpose.
- The roll geometry is guarded twice: the claim at the write, and the rail by construction. `TimeRailView.roll(surface:owner:owners:unclaimed:)` hands the rail that does not own a stand in nobody claims, and `drivesRoll` withholds the wheel relay and the scroll asks. **How to apply:** B3's glance changes that one function if it wants a minimap, and never hands a second rail `model.rollGeometry`.
- Open and on screen are two facts. The owner resolves from `editorWindowOpen` only (ADR-0033 says open and closed, and keeps visible for the deactivation sentence), so a miniaturized window still owns. `editorWindowCanTakeKeys` (open and on screen) is what the rest's deactivate skip and the activation's claim ask, and `PrimaryEditorWindowController.onScreen(miniaturized:key:)` is the one predicate behind it and the keyboard's return. Its `key` input exists because a window leaving the Dock can be key before `isMiniaturized` drops, and it is reported at the key loss too so it cannot latch. **Never feed the fact from `isVisible` or the occlusion callback:** ⌘H made it false and the word that made it true again arrived after `applicationDidBecomeActive` had read it, so the card rose over a visible editor window with Settings key. Both readers run in an active app and activating unhides, so a hidden app is no input. The reopen reads open on purpose and `show()` deminiaturizes, since the reopen answers false to AppKit.
- A key gain says who and never why. The editor window keyed while the panel owns is a claim unless the keyboard is coming back from a window of ours: `auxiliaryWindowReleasedKeys` (any key window's `willClose`, armed for one turn) or the modal bracket (`ModalSession.isBracketed`, which covers the order out inside `runModal` after `isRunning` has gone false). Then the turn is `.returnsKeysToOwner`, nothing moves, and `handKeysBack` raises as an activation a turn later. **Why one turn:** a claim misread as a return takes the keyboard from the window the person clicked, and a missed return is only the old behaviour. Unverified on hardware that AppKit re keys inside the close.
- Tests wait for the editor's main queue hops by order, never by the clock: `drainMainQueue()` (CompanionKitTests/MainQueueDrain.swift) queues a block behind the hop and waits on an expectation, three rounds deep. **Why:** a fixed 50 ms `RunLoop.run(until:)` failed the caret and line hand off test one full run in three, since other tests' timers used the stretch up before the main queue was serviced. Older pumps of the fixed kind still stand in RestoreFailureTests, FileDocumentTests, PersistenceRoundTripTests, ClipboardClearLifecycleTests, ConcealWireTests, EditorPersistenceTests and StanceFadeTests.
- After a modal, `handKeysBack` runs ahead of `modalSessionEnded`'s raise (the key gain is inside the bracket, the end is posted after), so two raises follow one open panel. `handsKeysBackToPanel` declines a panel that already holds the keys, which does not remove that second raise. Declining it in `raisesAfterModal` would silence the raise after every modal with no editor window, a routing call left for B4. The `ownership` log line `key gain=editor-window turn= armed= modal=` is how hardware answers whether the one turn arm was still set.
- Removing the guard in `BackdropModel.raise` exposed two things it had hidden: ⌘Tab back with the editor window open raised the panel (now claimed in `applicationDidBecomeActive`), and the rest's `editorWindowOpen` branch skipped the key relay on the hotkey path. Related: [[adr-0034-altitude-keeper]].
