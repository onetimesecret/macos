# Law 0002: Copy

Complete draft for review under [behaviour law conventions](README.md); do not
build against it as an accepted law. [ADR-0037](../adr/0037-explicit-clipboard-operations.md)
consumes this proposed rule. An empty decision list means no numbered accepted
design record incorporates the broader copy contract yet.

## The rule

Proposed governing wording:

> A deliberate copy command determines which selected content and
> representations leave OnetimePad.

The command identifies its source and consequence. Copying visible ink,
copying a supplied path, and copying decrypted contents are distinct operations.
A path or application association selects context; it does not authorize copying
another application's contents.

## Why this rule

The primary authority for the exploration's limit is the maintainer's
2026-10-01 instruction, exactly:

> we are not interested in background clipboard collection, or any automatic copying of information that is not readily available in the given context. Paths, applications, and what NSPasteboard/UTI can afford.

The proposed rule makes that limit reviewable at each write. Accepted
[Law 0001](0001-sealed-object.md#sealed-fragment-representation) supplies the
sealed-fragment invariant, exactly:

> The envelope never contains a sealed payload or ciphertext.

Its [security invariants](0001-sealed-object.md#security-invariants) also state:

> Complete payload egress remains core-side.

These existing obligations apply within Law 0001's scope. The broader ordinary
copy and context-copy policy below remains proposed.

## Operation classes

- **Document copy:** writes selected visible ink and structural sealed references.
  Ordinary copy does not alter the document. Cut first offers the same selection,
  then removes it through the appropriate structural transaction.
- **Context copy:** writes a path or application identifier deliberately selected
  in the current interaction. Bound folders are metadata, not permission to read
  or copy folder contents. No context-copy feature is implied by this law alone.
- **Named declassification:** writes a complete sealed payload through Law 0001's
  existing named, core-side operation. Decrypted drag is a separately labelled
  egress class, not an ordinary copy modifier invented by this draft.

Public and private representations belong to the same selected source. Extra
representations must not silently add unselected context or sealed payload.
Writing to a pasteboard is external transfer; undoing an editor action does not
recall the copy from a recipient.

## The contract

Rows marked owed have no dedicated coverage yet. Existing tests listed here pin
only their named behavior; they do not prove this whole law or release support.

| Interaction | Class | Proposed behavior | Pinned by |
| --- | --- | --- | --- |
| Copy selected visible ink | document copy | Offer only the selected ink in documented public representations; an empty selection writes nothing | owed: no issue yet, selection/offer tests |
| Copy a selected supplied path or app identifier | context copy | Offer that identifier only; perform no document or directory-content acquisition | owed: no issue yet, context-copy tests if this command is introduced |
| Copy sealed or mixed selection | document copy | Preserve ordered ink and UUID references in the private fragment; use public placeholders; include neither payload nor ciphertext | accepted authority: Law 0001; owed: issue 170 |
| Cut sealed or mixed selection | document copy / structural editing | Offer the same fragment and detach all selected objects atomically; retain Law 0001's undo and lifecycle semantics | accepted authority: Law 0001; owed: issue 170 |
| Copy decrypted contents | named declassification | Retain the named core-side egress; do not consume the object or turn ordinary copy into payload export | accepted authority: Law 0001; shell naming: `DocumentOpsTests.swift` `testTheChipMenuOffersPlaintextByName` |
| Guarded general-pasteboard clear | named egress follow-up | Follow accepted D-43's core-owned interval and ownership guard; leave a newer write untouched | `crates/ffi/src/lib.rs` `the_clear_interval_is_the_core_constant`; `crates/pasteboard/src/lib.rs` and `macos.rs` `clear_after_copy_only_clears_our_own_write` |
| Activate app, choose pad, inspect association, hover picker | no transfer | Make no clipboard write and acquire no clipboard content | owed: no issue yet, clipboard-access instrumentation |

## What the rule forbids

- Automatic copy on activation, association, suggestion, picker hover, or sort.
- Copying other applications' contents because their identity or a path is known.
- A hidden payload in an ordinary or app-private representation.
- A label implying that copying recalls earlier copies or erases recipients.
- Clearing a later write owned by another operation.

## The rubric for a new interaction

Identify the invoked command, selected source, destination pasteboard, offered
representations, and operation class. Does any representation export a sealed
payload? Does a cut remove more than the successfully offered selection? Is any
content being acquired before the explicit command? Which test or owed row pins
the answer?

## Acceptance and tests

Acceptance needs selection and offer tests, clipboard-access instrumentation for
context-only interactions, and the appropriate core/seam/shell tests for sealed
operations. A write failure must not trigger cut removal; coverage is owed for
each implemented cut route. New public representations need an explicit offer
policy before implementation, rather than treating every available format as
approved. The existing sealed contract remains authoritative while these broader
rows await review and coverage.

Accepted [D-43](../spec/design/2026-0916-clipboard-clear-interval.md)
states the retention limit exactly:

> It does not bound retention by clipboard managers, Universal Clipboard,
> other observers or receiving applications, and it makes no erasure or
> retention claim about the drag pasteboard.

This draft therefore makes no local-only delivery or observer-erasure promise.
Validate each shipped copy route on the supported macOS releases before any
compatibility claim; the mockup provides no such evidence.
