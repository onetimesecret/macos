# Multi device sync

**GitHub milestone:** [Multi device sync](https://github.com/onetimesecret/macos/milestone/3)  
**Status:** Active  
**Source of execution status:** GitHub issues, not this document.

## Goal

A user with two machines can open the same page on both and see the same text, without the server that carries it between them ever being able to read a word. Sync is off until the user turns it on, the pad keeps working with no account and no network, and a page that dies on one machine dies on the other.

The shape is already decided in part. [ADR-0013](../adr/0013-document-provenance-and-block-metadata.md) settles that sync follows broadcast rules rather than archive rules: a second device joins the stream at the current key frame and structurally never receives the ops behind it, compaction under collaboration is a coordinated protocol event rather than a local one, and a relay holds at most the encrypted deltas since the last key frame, purged by the ceremony, so what a compromised relay can accumulate is bounded by one GOP rather than by the life of the page (`docs/adr/0013-document-provenance-and-block-metadata.md:410-431`, `:507-511`). ADR-0020 is the next number and does not exist yet; it is where the relay itself gets decided. What it must reach into is spread across the tree: the key derivation and its rotation triggers in `crates/ffi/src/persist.rs`, the Loro seam in `crates/core/src/document.rs`, the compaction triggers and the expiry clock in `crates/core/src/store.rs`, the monotonic discipline in `crates/core/src/clock.rs`, and the network boundary that `crates/transport/src/lib.rs` enforces. [ADR-0016](../adr/0016-content-persists-across-restart.md) section 3 constrains the keys, because the keychain half is deliberately `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` so that no durable key rides iCloud Keychain to a second machine (`docs/adr/0016-content-persists-across-restart.md:202-262`). [ADR-0017](../adr/0017-durable-tabs-expiring-pages.md) decides that the rung is a tab property and the page is the thing that expires, which is the object the deadline rule has to agree about.

The tension is not resolved, and this plan does not pretend it is. The design documents forbid what ADR-0013 licenses. `docs/spec/design/01-problem-space.md:175-177` lists "Not a sync service. No cloud, no accounts for the core loop, no state that outlives the machine" as an anti goal. `docs/spec/design/03-design-principles.md:66` settles the iCloud sync question with "No", and `:85-88` states the principle a relay breaks most directly: promotion is the only network operation, it is unmistakably an action and never a side effect. `docs/spec/design/05-technical-direction.md:107-109` draws the boundary as exactly one outbound destination, TLS only, on explicit promotion, and `crates/transport/src/lib.rs:42-49` refuses any URL that does not start with `https://` before a socket opens. ADR-0013 answers the multi device question in the other direction. Both statements are load bearing, both are quoted to users, and nothing below can be built until they agree in writing. That reconciliation is pass 1, and it is allowed to come out either way.

## Completion criteria

- The design documents and ADR-0013 say the same thing about sync, and the network boundary is written as it will be rather than as it was.
- ADR-0020 records the relay decision, the pairing model, the metadata the relay unavoidably learns, and the join rule, each as a numbered section with its rejected alternatives named.
- A delta can leave one document, cross a wire, and land in another without a Loro type crossing out of `crates/core/src/document.rs` and without a peer id crossing a ceremony boundary.
- Ciphertext the relay retained before a ceremony cannot be opened after it, proven by a test rather than promised by a policy.
- Two devices holding one page agree on when it dies, and the earlier deadline is the one that fires.
- A device is trusted because a human verified it, not because it presented an account token.
- With sync off, the app is indistinguishable from today's app, and every degraded sync state has a sentence a user can act on.

## Pass 1: reconcile the doctrine before deciding anything

**Tracking:** [#92](https://github.com/onetimesecret/macos/issues/92)

This pass precedes every other one because an ADR cannot contradict the documents it sits under, and because four of the issues below cite the anti goal as a constraint on their own design.

- Decide whether the "not a sync service" anti goal is retracted, narrowed, or kept with sync as a named exception, in the words of the documents that carry it: `docs/spec/design/01-problem-space.md:175-177`, `docs/spec/design/03-design-principles.md:66`, `README.md`, and `docs/purpose-aspirations-and-peers.md`.
- Restate the network boundary in `docs/spec/design/05-technical-direction.md:107-109` for a second outbound destination, and say what still holds without change: TLS only, no telemetry, no update pings beyond the launch time release feed check.
- Decide what happens to the principle that promotion is the only network operation and is never a side effect (`docs/spec/design/03-design-principles.md:85-88`). A relay uploads as a consequence of typing, not of a gesture, so the principle either narrows to promotion specifically or it does not survive.
- Write down the conditions sync must meet to stay inside the design, somewhere an implementation issue can cite: off by default, opt in per account, visible while it runs, and a core loop that still works with no account and no network per `docs/design-brief.md:76`.
- Amend in place with a date, the house convention, rather than rewriting history.

## Pass 2: decide the relay, the join, and the clock

**Tracking:** [#93](https://github.com/onetimesecret/macos/issues/93), [#94](https://github.com/onetimesecret/macos/issues/94), [#100](https://github.com/onetimesecret/macos/issues/100)

ADR-0020 is one document and these are three issues, because two of the decisions it must record are large enough to argue separately and neither is settled. #94 and #100 land as numbered sections of the same ADR. This pass precedes pass 3 because every seam below is built against an answer here: the transport key exists to make purge structural, the pairing exchange exists because the account is not the device, and the delta seam has to carry whatever the deadline rule says travels.

- ADR-0020 follows the layout of ADR-0016 and ADR-0017: numbered subsections under Decision so issues can cite "ADR-0020 section 4", `**Required work.**` paragraphs separating what exists from what does not, named alternatives with their rejections, and `path:line` citations.
- Record the purge commitment as structural. Each GOP's deltas are sealed under a key derived at the key frame, the ceremony rotates it, clients destroy the outgoing one, and retained relay ciphertext is then undecryptable. State it that way and never as a deletion promise, per ADR-0007 on retired language.
- Record that the account is not the device. Account authentication gates channel access; it must never be the reason two devices trust each other, and the relay never distributes or escrows a content key.
- Record the metadata admission as a section of its own, not a sentence: account identity, device count, delta timing, delta sizes. The ledger's content free discipline is the standard to hold it to.
- Settle the delta from ADR-0013 plainly: the relay storage contract, the pairing model, and what becomes of ADR-0010's stance that two running form factors are two core instances with two stores (`docs/adr/0010-form-factors-as-sibling-targets.md:80`).
- #94: ratify what the relay holds for a device that enrols while every peer is asleep. Holding exactly one encrypted key frame per channel, superseded at each ceremony, serves the new laptop case and keeps storage bounded, at the cost of widening what a compromised relay holds at any instant from one GOP of deltas to those deltas plus the state they apply to. Requiring an online peer keeps the relay thinner and fails the case people will judge the feature by. Whichever wins, say what supersession means when a ceremony fails partway, and what the waiting device shows the user.
- #100: decide whose clock expires a page. Deadlines today are `Instant` values on a sleep inclusive monotonic clock (`crates/core/src/clock.rs:19-31`), and wall time is explicitly never used for expiry math, only for stamping records a human reads (`:23-26`); two readings of the monotonic clock are comparable only inside one boot session (`crates/ffi/src/lib.rs:1491-1493`). A restart already crosses that gap once under ADR-0016 section 4. Sync needs the crossing continuously, between machines whose clocks are set independently. Decide what travels, and decide that the earliest deadline any device believes in is the one that fires, because a page dying early is recoverable and a page living too long is the failure this app exists to prevent.
- #100 also owes a merge rule for the hold. `pause_press` is a three state machine per page: the first press holds for one hour, a press while held tops up to twenty four hours from now and never cumulatively, a press while topped up releases (`crates/core/src/store.rs:1160-1196`). Two devices running it independently need a rule, and the shorter hold is not obviously right when one device is deliberately holding a page open. Say what a second device does with `expire_due`, which entombs locally and writes an `Expired` record to that device's own ledger (`crates/core/src/store.rs:1266-1290`), now that two ledgers will describe the same page. Say what the app does when the numbers claim a page died before it was created.

## Pass 3: build the seams and the keys

**Tracking:** [#95](https://github.com/onetimesecret/macos/issues/95), [#96](https://github.com/onetimesecret/macos/issues/96), [#97](https://github.com/onetimesecret/macos/issues/97), [#98](https://github.com/onetimesecret/macos/issues/98)

Four independent pieces that can proceed in parallel once ADR-0020 lands, because none of them needs another's output to be designed. All four precede pass 4: the protocol cannot be specified without knowing what a delta looks like on the wire, and the ceremony cannot be coordinated without a key to rotate.

- #95, the per GOP key. What exists is one content key per form factor per state directory, `HKDF(keychain_half, file_half)` under a single versioned info string (`crates/ffi/src/persist.rs:204`, `:445-452`), with a second info string deriving the file half's filename (`:214`). Rotation exists as `rotate_key_halves` but fires on the two triggers ADR-0016 section 6 names rather than at a compaction boundary, and it erases rather than deriving forward (`crates/ffi/src/persist.rs:376-382`). Add a third derivation branch producing a per GOP transport key under its own versioned info string, documented beside the other two. Settle first whether it descends from the content key or from a separate pairing secret, because that answer decides whether a paired device that has never held a page can decrypt anything.
- #95 also has to answer ADR-0016 section 3. The keychain half is `ThisDeviceOnly` precisely to keep a durable key out of iCloud Keychain (`docs/adr/0016-content-persists-across-restart.md:202-262`), so the transport key cannot ride the existing mechanism to a second device and must arrive by pairing. The ledger key stays outside all of this: rotation must never touch it (`crates/ffi/src/persist.rs:188-196`).
- #96, the delta seam. `crates/core/src/document.rs` is deliberately the only file that touches Loro, and it exports exactly one shape: the full document with history included (`:214-220`), imported by a merge that is never partially applied (`:225-230`). Across the C ABI the shell speaks JSON op batches through `companion_sheet_apply_ops`, with `companion_sheet_sync_document` as the whole document recovery path. Deltas since a known point, and the version vector needed to ask for them, have no representation anywhere in the tree. Add both directions in the crate private style the file enforces, with the same reject whole discipline on import, and decide whether the frontier travels as opaque bytes or as structured JSON like the op batches.
- #96 has two constraints it must not break. A remote update that adds or removes a chip has to reach the same invariant check the local path goes through, or the chip roster and the document's marks fall out of one to one agreement, which restore treats as damage and refuses (`crates/core/src/persist.rs:152-156`). And a peer id must not cross a ceremony boundary: the compaction rebuild types the body run by run into a fresh document precisely because the spike measured that a `StateOnly` export keeps the authoring peer id (`crates/core/src/document.rs:363-395`). Decide what to do about `set_change_merge_interval(0)`, set so every commit stays its own change, which is what makes provenance work and what makes deltas chattier (`crates/core/src/document.rs:82-89`).
- #97, device pairing. Two devices must trust each other directly, with a per device identity key, a human performed verification the user is able to fail, and a path by which the content key or the transport key reaches the new device given that the keychain half cannot travel. The nearest worked art is the BYOE local service, where the app holds an Ed25519 identity key in the Keychain as a third account and answers a challenge nonce before plaintext moves (`docs/spec/feature/byoe/local-service.md:103-111`); the BYOE README's own retraction is worth reading before adopting any of it. Revocation belongs here too: a lost device loses access at the next ceremony at the latest, and the user needs a way to say so. Pairing secrets stay separate from the promotion credentials in `crates/credentials`, and clearing one does not clear the other.
- #98, account access. Auth today is HTTP Basic with an `extid` and an API token, isolated behind the `AuthStrategy` trait so a swap is additive (`crates/ots-client/src/auth.rs:10-13`), with PASETO bearer tokens already named as phase 2 (`docs/spec/design/05-technical-direction.md:132`) and the desktop app's needs for long lived tokens, device shaped identity and offline grace already asked as open question 19 (`docs/spec/design/06-open-questions.md:147-150`). OAuth gates the relay channel and nothing else. Settle which flow a desktop app with no browser and no redirect target uses, token lifetime and refresh for an app that sleeps for days, and what the relay does with a token that expires mid session. Sync credentials stay separate from promotion credentials, because promotion is a deliberate act and sync is a background one, and an expired token disables sync while leaving the pad fully usable.

## Pass 4: specify the protocol and coordinate the ceremony

**Tracking:** [#99](https://github.com/onetimesecret/macos/issues/99), [#101](https://github.com/onetimesecret/macos/issues/101)

These two are one event described from two sides, which is why they share a pass: the ceremony is a protocol message set, and the protocol's storage contract only means anything because the ceremony ends it. Both need pass 3's key and delta seam in hand, and both precede pass 5 because the app cannot show a user a state the protocol has not defined.

- #99 turns ADR-0013's bound into a protocol: the channel model and what a device attaches to, the message set for attach, publish, fetch since frontier and announce ceremony, the storage contract as a numbered section ADR-0020 can cite, and the backpressure limits a page held open for a week with every commit its own change makes necessary.
- #99 must say what happens when a device announces a ceremony and then dies before the others follow, and must check the metadata admission against the protocol as specified rather than as imagined.
- #99 has a transport constraint it cannot ignore. `crates/transport/src/lib.rs:42-49` hard refuses any non `https://` URL before a socket opens. A relay wanting a long lived connection either lives inside that constraint or the constraint is amended deliberately, in the same amendment pass 1 makes, not incidentally as a side effect of shipping.
- #99 also owes the server side. The relay work is filed in the onetimesecret repo, with this issue naming the interface it must implement. A device offline for longer than one GOP recovers by rejoining at the current key frame, never by asking for history.
- #101 makes compaction coordinated. Today it is purely local: `Sheet::compact` graduates block metadata and rebuilds the document, fired from an accepted `cycle_rung` (`crates/core/src/store.rs:1093-1115`), an accepted `set_rung` (`:1122-1141`), and a pause top up (`:1160-1196`). With peers, each of those becomes a proposal the other devices accept, perform, and confirm.
- #101's interesting case is failure. A device asleep during a ceremony holds pre ceremony history and rejoins carrying it, and it is either refused until it drops that history or the ceremony was never a boundary. Rotating the transport key and rebuilding the document are two halves of one event and must not be able to half happen. A ceremony proposed and not confirmed by every attached device leaves everyone on the old GOP rather than splitting them across a boundary.
- #101 must leave solo behaviour exactly as it is. With no peer attached a device still compacts at rung transitions, with a test that proves it, and the pad must not appear frozen while a ceremony runs on a gesture the user just made.

## Pass 5: give sync a surface

**Tracking:** [#102](https://github.com/onetimesecret/macos/issues/102)

Last, because every sentence the app shows names a state some earlier pass defined, and because the off switch is the promise pass 1 either kept or amended. Whatever the documents settle, the app is where a user finds out that something now leaves the machine without a gesture.

- Sync is off by default, and the app with sync off is indistinguishable from today's app.
- Enrolment is where #97's verification appears: the fingerprint or short authentication string on both devices, with a way to fail it, plus a device list showing what is attached, when each was last seen, and how to revoke one.
- Status follows the persistence word the header already carries from the write lifecycle, saving, saved and save failed, rather than inventing a second vocabulary.
- Every degraded state gets its own sentence and none of them are silent: an expired token from #98, a relay that cannot be reached, a device waiting to join with no peer awake from #94, and a page being edited elsewhere.
- No second settings surface. The controls live in the existing Settings surface with the keymap file as the source of any shortcut, and a control that should exist only while it is needed reuses the shape of the ledger's clear button behind its unavailable ledger banner. `HiddenUI` from #78 is the recent lesson about affordances that had not earned their place.

## Dogfood loop

Keep new observations in [ABERRATIONS.md](../dogfood/ABERRATIONS.md). Promote each one to an ADR, GitHub issue, plan, or [DOGFOOD.md](../dogfood/DOGFOOD.md) guidance once it is understood. Link the destination from the original observation. Sync observations belong here too, and one of them outranks the rest: anything that leaves the machine when the user did not ask for it is an aberration whatever the documents say, and it goes straight to an issue.
