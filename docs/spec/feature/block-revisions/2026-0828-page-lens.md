# The page lens: page history as a second projection

Side doc to [`README.md`](README.md) · captured 2026-08-28.
A concept note, deliberately unscheduled: nothing here is committed
to build. Recorded because the architecture makes it nearly free and
because two of the spec's own rescue scenarios turn out to need it.

## The observation

In the one sense that matters, the page is already a block of
blocks: there is a single op log for the whole page, and a block is
nothing but a projection of it (`BlockIndex` is policy over the flat
stream, ADR-0013). ADR-0025's block revisions are that log filtered
through one block's anchor. A page-level history is the same log
with the filter removed: fork at a frontier, render all runs instead
of one block's span.

The consequence for cost: the op log does not grow by one byte for
this. Both lenses read the history the log already keeps, and
ADR-0025 part 2's size budget governs both identically. The only
new spend is read-time (a whole-page render per scrub position
instead of one block's text) and it evaporates when the surface
closes, same as the block derivation.

## What this is not

Not the block-tree. The heavy version of "page as a block of
blocks" would make blocks first-class in the data model, a movable
list of block containers, so that a reorder is a recorded move op
with identity. That is ADR-0013's architecture 1 and stays a named
rejection: it ends the little-text-file contract. This concept
requires nothing from it.

Not a mode. A mode that hides the block-grain interface and shows a
page-grain one would create the mental state it is trying to avoid.
The shape is a zoom level: two doorways into one timeline. The
stamp is the block's doorway (spec capability 2); the page gets its
own doorway (the tab, or a page-level gesture), and both open
projections of the same history, so there is no state to track and
nothing to swap.

## Structural history without structural ops

Order-of-paragraphs history is derivable at display time: diff page
states between boundaries and detect moves by content matching, the
direction `docs/research/2026-0828-line-diffing.md` already points.
A reorder then shows honestly as "this paragraph moved" in the page
lens, without any structural event being stored. This also papers
over a derivation wrinkle: a move implemented as delete plus
reinsert re-stamps the moved characters, so op-level provenance
alone would misread a move as fresh writing; content-matched move
detection is what lets the display say what actually happened.

## Why the spec may eventually require it

Two of capability 1's rescue scenarios are page-grain events that
block revisions structurally cannot serve:

- **The select-all typed over.** The accident destroys every block
  at once. Block-by-block restoration reads as broken; the right
  rescue is one page-level take-back.
- **The dead block.** A deleted paragraph has no stamp, so it has
  no doorway. "Any text a block has ever shown can be gotten back"
  is currently only true for blocks still alive. The page lens is
  the only place a dead block's text can be found again.

So if this ships, it belongs under capability 1's umbrella as the
page-grain rescue path, not as a separate feature with its own
justification.

## The trap to defuse on arrival

Capability 5 names whole-page restore as the standing incumbent
complaint: reverting the page in Docs or Notion sacrifices
everything changed since. ADR-0025's construction already defuses
it, a page restore is one ordinary commit and the pre-restore state
becomes the newest recoverable state, but the page lens must say so
on its surface, because users arriving from those apps bring the
fear with them.

## Status

Concept only. Open when block revisions (ADR-0025 part 1) have
shipped and dogfood has opinions; the dead-block gap is the likely
forcing event.
